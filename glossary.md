## The GPU stack

- <a name="g-vulkan"></a>**Vulkan** — Khronos' low-level GPU API, and the reason a 2019 AMD GPU is usable on macOS at all: ggml ships a Vulkan compute backend, so the same kernels that run on Linux and AMD run here. ([spec home](https://www.vulkan.org/))
- <a name="g-moltenvk"></a>**MoltenVK** — an implementation of Vulkan on top of [Metal](#g-metal): every Vulkan call is translated at runtime. Faithful enough to run llama.cpp, and *not* faithful enough to preserve every guarantee a compute shader assumes, which is the origin of most [known issues](README.md#known-issues). ([repo](https://github.com/KhronosGroup/MoltenVK))
- <a name="g-metal"></a>**Metal** — Apple's native GPU API, and the wrong choice on this machine. It assumes unified memory; on a discrete GPU, ggml's Metal path re-reads weights across PCIe on every token. ([docs](https://developer.apple.com/metal/))
- <a name="g-icd"></a>**ICD / `VK_ICD_FILENAMES`** — an *Installable Client Driver* is the actual Vulkan driver the loader opens. Building against Homebrew's `vulkan-loader` rather than linking `libMoltenVK` directly means this environment variable picks the driver at runtime, so you can swap MoltenVK for another implementation without rebuilding. ([loader interface](https://github.com/KhronosGroup/Vulkan-Loader/blob/main/docs/LoaderDriverInterface.md))
- <a name="g-rdna1"></a>**RDNA1** — the architecture of the Radeon Pro 5500M (Navi 14). First-generation RDNA: no matrix cores, and no integer dot product the API can reach, so several well-tested ggml fast paths are unused here. See [RDNA generations](hardware.md#rdna-generations). ([overview](https://en.wikipedia.org/wiki/RDNA_(microarchitecture)))
- <a name="g-dgpu"></a>**dGPU / iGPU** — discrete (the Radeon: 4 GB of its own VRAM behind PCIe) against integrated (a slice of system DRAM). Both enumerate under Vulkan, which is exactly the problem. Everything here targets the discrete GPU only.
- <a name="g-ggml"></a>**ggml / GGUF** — the C tensor library underneath all five tools here, and its single-file model format (weights, metadata and quantization type). One shader fix in ggml therefore moves llama.cpp, ollama, LocalAI and stable-diffusion.cpp at once. ([ggml](https://github.com/ggml-org/ggml), [GGUF spec](https://github.com/ggml-org/ggml/blob/master/docs/gguf.md))
- <a name="g-shader"></a>**Compute shader / SPIR-V / `.comp`** — ggml's GPU kernels are GLSL compute shaders compiled to SPIR-V bytecode. Several fixes on these branches are edits to `.comp` files. ([SPIR-V](https://www.khronos.org/spir/))
- <a name="g-subgroup"></a>**Subgroup and workgroup (`gl_SubgroupInvocationID` against `gl_LocalInvocationID`)** — a *workgroup* is the block of threads that share memory and synchronize together; a *subgroup* is the hardware-lockstep slice inside it. A shader assuming the workgroup is one contiguous, in-order subgroup relies on something MoltenVK does not guarantee — the root cause behind several [known issues](README.md#ki-subgroup-size). ([subgroup tutorial](https://www.khronos.org/blog/vulkan-subgroup-tutorial))
- <a name="g-test-backend-ops"></a>**`test-backend-ops`** — ggml's per-operation differential test: run each operation on a backend, compare against the CPU reference, and report the maximum error against a tolerance. The tool that converts "this model is broken" into "`SSM_SCAN` returns NaN". ([usage](ggml.md#run))
- <a name="g-visible-devices"></a>**`GGML_VK_VISIBLE_DEVICES`** — a ggml environment variable restricting which Vulkan devices are enumerated at all. `0` here means the Radeon is the only device that exists as far as ggml is concerned. The Vulkan analogue of `CUDA_VISIBLE_DEVICES`.

## Failure modes

- <a name="g-nan"></a>**NaN** — IEEE-754 "not a number". A single NaN propagates through every later matrix multiplication, so a broken shader surfaces as token salad or full-frame image noise rather than a crash. ([IEEE 754](https://en.wikipedia.org/wiki/IEEE_754))
- <a name="g-device-lost"></a>**`vk::DeviceLostError` (`VK_ERROR_DEVICE_LOST`)** — the GPU stopped responding; every Vulkan object belonging to it is invalid and the process can't recover. On this card it follows either a VRAM blow-up or sustained back-to-back GPU load. ([VkResult](https://registry.khronos.org/vulkan/specs/latest/man/html/VkResult.html))
- <a name="g-watchdog"></a>**GPU watchdog timeout (`kIOAccelCommandBufferCallbackErrorTimeout`)** — macOS kills a command buffer that runs too long, so the desktop stays responsive. Metal image generation trips it on every run here. ([MTLCommandBufferError](https://developer.apple.com/documentation/metal/mtlcommandbuffererror))
- <a name="g-spill"></a>**CPU spill** — when a model or its [KV cache](#g-kv) doesn't fit in VRAM, ggml keeps the overflow in host RAM and pays a PCIe round-trip for it. It shows up in the load log as a CPU buffer appearing, and in throughput as a cliff, not an error.
- <a name="g-throttle"></a>**Thermal throttling / `CPU_Speed_Limit`** — the current CPU clock cap in percent, readable with `pmset -g therm`. 100 is unthrottled; this laptop reaches 20–36 under two minutes of load. Counter-intuitively, *cooling* the machine makes the GPU numbers worse ([benchmarking.md](benchmarking.md#why-this-machine-lies-to-you)).
- <a name="g-ioreg"></a>**`ioreg` / `IOAccelerator` / `inUseVidMemoryBytes`** — macOS's IOKit registry, and the property that reports VRAM actually in use. The ground truth for "is the model really on the Radeon?" when a runtime's own reporting is unreliable. ([ioreg(8)](https://keith.github.io/xcode-man-pages/ioreg.8.html))

## LLM inference and serving

- <a name="g-kv"></a>**KV cache** — attention's cached per-token key and value tensors, so generating token *n* doesn't recompute tokens 1 to *n*−1. It grows linearly with context, it's the second consumer of VRAM after the weights, and on a 4 GB card it — not the model size — usually sets your [context ceiling](models.md#context-ceilings). ([explainer](https://huggingface.co/docs/transformers/en/kv_cache))
- <a name="g-kv-quant"></a>**KV precision (`f16`, `q8_0`, `q4_0`)** — the cache can itself be quantized, trading recall for context length (32 → 9 KiB per token). In llama.cpp this requires [flash attention](#g-flash-attn) and costs about 4%. Use q4_0; see the [q8_0 caveat](README.md#ki-q8-0) if you are not on these branches.
- <a name="g-ctx"></a>**Context size (`--ctx-size`, `n_ctx`, `context_size`)** — how many tokens the model can attend to at once, and the direct multiplier on [KV cache](#g-kv) size.
- <a name="g-prefill"></a>**Prefill and decode** — prefill (prompt processing) runs the whole prompt in parallel and is compute-bound; decode (token generation) emits one token at a time and is memory-bandwidth-bound. Different bottlenecks, which is why they're benchmarked separately as [pp512 and tg128](#g-pp512).
- <a name="g-flash-attn"></a>**Flash attention (`--flash-attn`, `-fa`, `OLLAMA_FLASH_ATTENTION`, `flash_attention`)** — an attention kernel that tiles the computation so the N×N attention matrix is never held in memory. Upstream, `FLASH_ATTN_EXT` is unsupported on Vulkan here and ggml runs attention on the CPU, costing about 3.5×; the subgroup-free path on these branches runs it on the GPU, where it is the faster option for generation. ([paper](https://arxiv.org/abs/2205.14135))
- <a name="g-quant"></a>**Quantization (`Q4_K_M`, `q8_0`, `--type q8_0`)** — storing weights below fp16. `Q4_K_M` is llama.cpp's "4-bit, medium" mix at about 4.5 bits per weight, the default sweet spot and what makes a 4B model fit in 4 GB. sd.cpp's `--type` quantizes a safetensors checkpoint while loading instead. ([k-quants](https://github.com/ggml-org/llama.cpp/pull/1684), [type table](https://huggingface.co/docs/hub/en/gguf#quantization-types))
- <a name="g-ngl"></a>**`-ngl` / `gpu_layers` / `num_gpu` (layer offload)** — how many transformer layers live on the GPU. `99` means all of them, `0` is CPU-only, and anything between splits the model and pays a PCIe hop per token. One knob, three spellings: llama.cpp, LocalAI, ollama.
- <a name="g-arch"></a>**Dense / GQA / hybrid / PLE** — the architecture column of the [fit table](models.md#speed-and-fit). *Dense*: attention in every layer, so the [KV cache](#g-kv) grows with context. *[GQA](https://arxiv.org/abs/2305.13245)* (grouped-query attention): several query heads share one key/value head, shrinking that cache. *Hybrid*: most layers are recurrent blocks with fixed-size state, so long context costs almost no memory. *[PLE](https://ai.google.dev/gemma/docs/gemma-3n)* (per-layer embeddings, Gemma): a large embedding table stays in host RAM while the compute core sits on the GPU, so "E4B" fits in far less VRAM than its parameter count suggests.
- <a name="g-ssm"></a>**SSM / Mamba-2 / `SSM_SCAN`** — the state-space model family and its selective-scan operation; `SSM_SCAN` is the ggml operation and Vulkan shader that implements it. It returned NaN on this stack until [the fix](ggml.md#changes-on-this-branch). ([paper](https://arxiv.org/abs/2405.21060))
- <a name="g-gdn"></a>**Gated DeltaNet / `GATED_DELTA_NET`** — a gated linear-attention variant with delta-rule state updates, used by Qwen3.5, and the second shader hit by the same bug. Its prefill is a sequential scan — thousands of tiny dispatches, which are cheap on a native driver and expensive through MoltenVK. ([paper](https://arxiv.org/abs/2412.06464))
- <a name="g-lfm2"></a>**LFM2 / short convolution / `SSM_CONV`** — Liquid AI's on-device hybrid architecture: most layers are gated short convolutions rather than full attention, so state stays small and generation is fast. The same operation family as [Mamba-2](#g-ssm), but verified correct here. ([LFM2.5](https://www.liquid.ai/blog/lfm2-5-2-6b))
- <a name="g-vlm"></a>**VLM / `mmproj` / image tokens** — a vision-language model pairs an LLM with an image encoder; in GGUF form the encoder and projector are a separate `mmproj-*.gguf`, and an image becomes N embedding slots ("image tokens"). More tokens means better grounding and proportionally more [prefill](#g-prefill), which is what `OLLAMA_IMAGE_MIN_TOKENS` trades off. ([llama.cpp multimodal](https://github.com/ggml-org/llama.cpp/blob/master/docs/multimodal.md))
- <a name="g-thinking"></a>**Thinking models / reasoning field / CoT** — models trained to emit a chain of thought before answering. Over an OpenAI-compatible API, the thinking text may arrive in `message.reasoning` while `message.content` stays empty until the block closes — behaviour that looks like a failure and isn't. ([CoT paper](https://arxiv.org/abs/2201.11903))
- <a name="g-openai-api"></a>**OpenAI-compatible API / `/v1/chat/completions`** — the de-facto REST shape that llama-server, ollama and LocalAI all speak, so any OpenAI SDK client works unchanged. ([reference](https://platform.openai.com/docs/api-reference/chat))
- <a name="g-grpc"></a>**gRPC backend (LocalAI)** — LocalAI doesn't link llama.cpp; it starts a `grpc-server` child process and talks [gRPC](https://grpc.io/) to it. That indirection is why the MoltenVK environment has to be carried by a wrapper script, and why the backend's ggml banner never reaches LocalAI's log.
- <a name="g-oci"></a>**OCI image** — the standardised container image format, used by LocalAI's backend gallery to distribute backends. Nothing here uses that path: every backend is built from source for Vulkan, because no published image targets an Intel Mac with a discrete AMD GPU. ([spec](https://github.com/opencontainers/image-spec))
- <a name="g-ppl"></a>**Perplexity** — the exponential of mean negative log-likelihood over held-out text; the standard check that a backend is numerically sane, since a broken GPU path diverges from the CPU immediately. ([definition](https://huggingface.co/docs/transformers/en/perplexity))

## Benchmarks and metrics

Full protocols: [benchmarking.md](benchmarking.md).

- <a name="g-pp512"></a>**pp512 / tg128** — `llama-bench`'s two workloads, both in tokens per second: **pp** is [prefill](#g-prefill) of an N-token prompt, **tg** is generation of N tokens. So pp512 is "how fast it digests a 512-token prompt", tg128 is "how fast it types". ([llama-bench](https://github.com/ggml-org/llama.cpp/tree/master/tools/llama-bench))
- <a name="g-toks"></a>**tok/s** — tokens per second; unqualified here it means generation. A token averages about ¾ of an English word.
- <a name="g-counterbalance"></a>**Counterbalanced A/B** — running A-then-B and B-then-A and reporting both rounds, so drift (here, GPU clock ramp and thermal state) cancels instead of accumulating against one arm. It's what caught a "3–14% regression" that turned out to be pure drift. ([counterbalancing](https://en.wikipedia.org/wiki/Counterbalanced_measures_design))
- <a name="g-sd"></a>**± and "sd"** — standard deviation across repetitions. It's the load-bearing number here: `10.88 ± 0.13` is a measurement, `14.30 ± 6.25` is noise wearing a mean's clothing.
- <a name="g-bfcl"></a>**BFCL-V4 / AST** — Berkeley Function-Calling Leaderboard: does the model emit the right tool call with the right arguments? *AST* scoring parses the emitted call and compares it structurally against the reference rather than executing it. ([leaderboard](https://gorilla.cs.berkeley.edu/leaderboard.html))
- <a name="g-mmlu"></a>**MMLU-Pro** — a harder MMLU: 10 options instead of 4, reasoning-heavy, run 0-shot with [CoT](#g-thinking). ([dataset](https://huggingface.co/datasets/TIGER-Lab/MMLU-Pro))
- <a name="g-math500"></a>**MATH-500** — a 500-problem competition-mathematics subset, graded by symbolic answer equivalence. ([dataset](https://huggingface.co/datasets/HuggingFaceH4/MATH-500), [math-verify](https://github.com/huggingface/Math-Verify))
- <a name="g-ifbench"></a>**IFBench** — AllenAI's verifiable instruction-following benchmark: prompts with programmatically checkable constraints, graded by 83 verifier functions rather than by a model. Deliberately hard. ([repo](https://github.com/allenai/IFBench))
- <a name="g-gpqa"></a>**GPQA Diamond** — 198 graduate-level, "Google-proof" science multiple-choice questions, four options, chance floor 0.25. A gated dataset: the harness needs an accepted licence and an `HF_TOKEN`. ([dataset](https://huggingface.co/datasets/Idavidrein/gpqa))
- <a name="g-longbench"></a>**LongBench-v2** — multiple-choice questions over long documents. ([dataset](https://huggingface.co/datasets/THUDM/LongBench-v2))
- <a name="g-mrcr"></a>**MRCR** — Multi-Round Co-reference Resolution: retrieve one specific earlier message from a long synthetic conversation full of near-identical distractors. ([dataset](https://huggingface.co/datasets/openai/mrcr))
- <a name="g-pipette"></a>**Pipette** — Liquid AI's open-source on-device benchmarking suite, measuring model × quantization × runtime × device performance on the device itself, with quality scored offline on reference GPUs. ([blog](https://www.liquid.ai/blog/pipette-on-device-ai-benchmarking-by-liquid-ai), [clients](https://github.com/Liquid4All/pipette-clients))
- <a name="g-clip"></a>**CLIP score** — cosine similarity between CLIP's embedding of the prompt and of the generated image; a reference-free proxy for prompt adherence. Scored for the image models in [stable-diffusion.cpp.md](stable-diffusion.cpp.md#image-quality). ([paper](https://arxiv.org/abs/2104.08718))

## Diffusion

- <a name="g-diffusion"></a>**Latent diffusion / steps / cfg-scale / sampler** — generation denoises a small latent image over N *steps*, then decodes it to pixels. *cfg-scale* is how strongly the prompt is enforced (turbo models want about 1, SD 1.5 about 7); the *sampler* is the integration rule. ([paper](https://arxiv.org/abs/2112.10752))
- <a name="g-unet"></a>**UNet** — the convolutional encoder/decoder that performs the denoising, and where nearly all the GPU time goes. ([paper](https://arxiv.org/abs/1505.04597))
- <a name="g-conv-direct"></a>**im2col convolution and `--diffusion-conv-direct`** — the default GPU path turns each convolution into one large matrix multiplication over an unfolded copy of the input, which is numerically broken on this [RDNA1](#g-rdna1) and MoltenVK stack. `--diffusion-conv-direct` convolves directly instead: correct, and about 3× faster. ([sd.cpp #563](https://github.com/leejet/stable-diffusion.cpp/issues/563))
- <a name="g-vae"></a>**VAE / VAE decode / `--vae-on-cpu`** — the autoencoder that turns the final latent into pixels. It's the *peak* VRAM moment of a run, so a model can load comfortably and still fail at the last step. Moving it to the CPU is the standard 4 GB lever. ([paper](https://arxiv.org/abs/1312.6114))
- <a name="g-turbo"></a>**SD-Turbo / SDXL-Turbo** — Stable Diffusion variants distilled to produce usable images in 1–4 steps rather than 20–50. That step reduction is what makes image generation practical on this card. ([paper](https://arxiv.org/abs/2311.17042))
- <a name="g-safetensors"></a>**safetensors** — Hugging Face's memory-mappable tensor format with no code execution on load; sd.cpp reads it directly, quantizing on the fly with `--type`. ([repo](https://github.com/huggingface/safetensors))
- <a name="g-lora"></a>**LoRA / ControlNet** — the two ecosystems that make an older base model worth keeping: small low-rank fine-tune adapters ([LoRA](https://arxiv.org/abs/2106.09685)) and structural conditioning on an edge, pose or depth map ([ControlNet](https://arxiv.org/abs/2302.05543)). SD 1.5 has by far the largest library of both.
